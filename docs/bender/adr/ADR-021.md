# ADR-021: Bender Identity, Versioning, and Serialization Foundation

**Date:** 2024-05-24
**Status:** Accepted

## Context
Bender requires a robust foundation for managing data artifacts. Artifacts need to have stable identities, be versioned to allow safe evolution without breaking historical data, and have a deterministic serialization format to enable reproducible verification and hashing. Crucially, the mechanism must be entirely independent of the `studium` application logic, database, or ORM migrations.

## Decisions

1.  **Identity:**
    *   `Id` will be represented as an opaque UUIDv4 string, encapsulated in an immutable value object. It is deliberately detached from paths, content hashes, or list indices to ensure a single conceptual entity retains its identity across modifications and storage moves.
    *   `Namespace` will be a string (lowercase alphanumeric and hyphens, max 64 chars) to categorise artifacts and domain boundaries.

2.  **Provenance:**
    *   We introduce a minimal `Provenance` model pointing back to source `Id`s and `Namespace`s, and an `OperationRecord` describing how the artifact was produced.
    *   This is distinct from the artifact's actual mechanics content.

3.  **Serialization and Fingerprinting:**
    *   Bender artifacts will serialize to a canonical UTF-8 JSON format (sorted keys, no spaces, rejected NaN/Infinity, rejected duplicate keys).
    *   We establish a deterministic SHA-256 `fingerprint` computed *only* over the semantic payload and schema/namespace, intentionally excluding the `Id` and `Provenance`. This allows us to mathematically confirm when two independently generated artifacts are structurally identical despite having different origins.

4.  **Versioning and Envelope:**
    *   All serialized payloads will be wrapped in a `VersionedArtifact` envelope containing `id`, `namespace`, `schema_name`, `schema_version`, `payload`, and `provenance`.
    *   Schema versions are simple integers (1, 2, 3...).

5.  **Schema Migrations:**
    *   Instead of evolving the data structure in place, we implement a pure, function-based `SchemaMigrationRegistry`.
    *   Older payloads are explicitly transformed step-by-step (e.g., v1 -> v2, then v2 -> v3) via registered pure functions before being loaded into the current runtime classes.
    *   Migrations preserve `Id` and `Provenance`.

## Consequences
*   **Positive:** Safe, long-term storage of Bender artifacts; explicit and testable upgrade paths; strong foundations for cross-validation without false negatives due to JSON key ordering.
*   **Negative:** Developers must write explicit migration functions whenever a payload schema changes; slightly more boilerplate when saving/loading artifacts.
